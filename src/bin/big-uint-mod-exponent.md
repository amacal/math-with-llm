# BigInteger Modular Exponentiation

## Overview

This session ports square-and-multiply modular exponentiation from fixed-width integers, as implemented and proved correct in "Modular Exponentiation" (`src/bin/mod-exponent.rs`), to the arbitrary-precision `BigNumber` type used throughout this repo's BigInteger arc. The computational problem does not change: given a base, an exponent, and a modulus, compute base raised to the exponent, reduced modulo the modulus, without ever materializing the full unreduced power. What changes is that all three quantities — base, exponent, and modulus — are now `BigNumber` values with no fixed bit width, and every arithmetic step (squaring, conditional multiplication, and reduction) must itself be implemented with the file's own from-scratch multi-limb addition, subtraction, multiplication, and division. The motivating reason the exponent in particular must be arbitrary-precision, rather than a native integer, is that in the cryptographic uses this session is building toward, the exponent can be exactly as large as the modulus: Miller-Rabin's witness test raises a base to the power d, where d is derived from n minus one for the candidate prime n, and RSA's private and public exponents live in the same range as its modulus. The base, too, is arbitrary-precision in these settings, since it stands for a message or ciphertext that can occupy the full width of the modulus.

Because the governing invariant, the induction proving it is maintained, and the termination argument are identical in shape to the native-integer version, this file cites "Modular Exponentiation"'s correctness argument by name rather than re-deriving it from scratch, restating only the exact formulas needed to tie that argument to the limb-level implementation here. What is genuinely new in this session is the complexity analysis once every intermediate value is itself a multi-limb number rather than a machine word, a bit-extraction design choice that only matters once the exponent can span many limbs, and an edge case in how the running product is initialized that the fixed-width version never had to confront.

## Reading exponent bits without shifting

The native-integer version tests the exponent's low bit and then right-shifts the whole exponent by one position every iteration, which is free when the exponent fits in one machine word. For a multi-limb `BigNumber` exponent, repeatedly shifting the entire value right by one bit is not free: a single shift touches every limb to carry bits across limb boundaries, so shifting once per bit processed costs work proportional to the number of limbs, and doing this once per bit of the whole exponent multiplies that cost by the number of bits. This session's implementation avoids that cost entirely by never mutating the exponent at all. Instead, it walks the exponent's limb vector outer-to-inner and, within each 64-bit limb, tests each of the 64 bit positions directly via a shift-and-mask against that single limb, which is a constant-time operation on a fixed-width `u64`. Reading one bit this way costs constant time regardless of how many limbs the exponent has, so the total cost of extracting every bit of the exponent is proportional only to the number of bits, not to the number of bits multiplied by the number of limbs, which is exactly the saving the destructive-shift approach would have given up.

## Correctness

The invariant, the induction that maintains it, and the termination argument are identical in content to those already proved in "Modular Exponentiation"; only the mechanism for advancing from one bit to the next differs, from shifting the whole exponent right each step to indexing directly into its limbs, and the invariant itself is phrased purely in terms of how many bits have been processed, not how they were read. Restated for this implementation, after k bits of the exponent have been processed, the following two facts hold together, where n is the modulus:

$$
\text{power} = \text{base}^{2^k} \bmod n \qquad \text{result} = \text{base}^{\,\text{exp}\,\&\,(2^k-1)} \bmod n
$$

The left equation says that power always holds the base raised to the k-th power of two, reduced mod n; the right equation says that result always holds the base raised to exactly the low k bits of the exponent, reduced mod n, with every higher bit treated as zero. The base case, the squaring step that advances power, the disjoint-bit argument showing the conditional multiplication never causes a carry into bits already accounted for, and the termination condition once every remaining higher bit is zero, all carry over unchanged from "Modular Exponentiation"'s own correctness argument and are not repeated here. What is genuinely new at this limb-indexed level is how the invariant is kept concretely true: power is reduced modulo the modulus via division immediately after every squaring, and result is reduced the same way immediately after every conditional multiplication, so neither variable is ever allowed to grow across iterations regardless of how many limbs it occupies.

## Complexity

Let eb denote the number of limbs in the exponent and mb the number of limbs in the modulus. The outer loop runs once per limb of the exponent, and the inner loop runs 64 times per limb to cover every bit, so the total iteration count is 64 times eb. Within a single iteration, the dominant cost is one schoolbook multiplication of an mb-limb number by itself (and, when the bit is set, a second multiplication of the same size), each costing time proportional to mb squared, followed by a division that reduces a roughly 2·mb-limb intermediate back down to mb limbs; as established in "BigInteger Division," the cost of that long-division reduction is itself proportional to the product of the divisor's limb count and the gap between the two operands' limb counts, which for an intermediate of this size is the same mb-squared order as the multiplication. Combining the per-iteration cost with the iteration count gives an overall running time proportional to eb times mb squared. In the cryptographic settings motivating this session, the exponent and the modulus are comparable in magnitude, so eb and mb are the same order of magnitude, and the bound collapses to a single-variable cost proportional to mb cubed.

## Edge cases

The first implementation guarded only against a zero modulus, returning none in that case, and initialized the running product result to the literal value one without reducing it modulo the modulus. This was invisible in every test where the exponent was nonzero, because the main loop's first conditional multiplication would reduce result the moment any bit was processed; it only surfaced when the exponent was zero and the modulus was exactly one, since the loop body then never executes at all, leaving result at the unreduced value one instead of the mathematically correct zero. An alternative design was considered — rejecting any modulus of one or less outright and returning none, on the reasoning that a modulus of one never arises in a real RSA or Miller-Rabin setting — but this session instead chose the more general fix of initializing result to one reduced modulo the modulus directly, via the same division operation already used elsewhere in the loop. This fix costs nothing extra asymptotically: for any modulus of two or more, dividing the single-limb value one by a larger number short-circuits through the existing less-than check in the `Div` implementation without performing any long division at all, so the added reduction is constant time regardless of how large the modulus is.

## Worked example

Take base equal to three, exponent equal to five, and modulus equal to seven, all represented as single-limb `BigNumber` values; five in binary is 101, so bit 0 and bit 2 are set and bit 1 is clear. Initialization gives power equal to three mod seven, which is three, and result equal to one mod seven, which is one. At k equals zero, bit 0 of five is set, so result is first updated to one times three mod seven, which is three; power is then squared to three times three mod seven, which is nine mod seven, giving two. At k equals one, bit 1 of five is clear, so result stays at three; power is squared to two times two mod seven, which is four. At k equals two, bit 2 of five is set, so result is updated to three times four mod seven, which is twelve mod seven, giving five; power is squared again but no longer affects the outcome, since every remaining bit of the exponent is zero. The loop finishes with result equal to five. This can be checked directly: three raised to the fifth power is two hundred forty-three, and two hundred forty-three divided by seven is thirty-four remainder five, confirming the traced result.
